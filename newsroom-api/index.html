The reader API: a map, and a review

Everything a reader does on this site, before it moves: the files and their hashes, what a reader can click, type or pay, where their data goes, the contracts other sites and agents program against, and what a line-by-line review found.

“API” here means what the brief means by it: client-side. Components, formats and contracts the browser runs, with no server of ours and nothing to deploy but files. It is what other sites and agents program against: the meter’s configuration, the reading-list link, the article numbers, the persona links, the share’s envelope. This page maps all of it as it is at v0.12.104, before anything moves, and reviews it. It is regenerated on every build from the tree, and from the tables kept beside the code in admin/build/api_map.py; the same map is map.json, and the review is also a note.

What the hashes are for. The brief’s rule for the move is that the live site serves the same bytes after it as before, proved by hash and not by reading the diff. The hashes below are that “before”: scripts, styles and JSON raw; pages with the site chrome and version stamps normalised, as the gate already does for imported pages. They change when the files change, and they are meant to.

In numbers

Reader code that runs in a browser11,101 lines in 51 files; 8,735 more lines in 28 frozen files of earlier meter versions, served and never changed
Pages that carry it30 pages written for it; the balance chip and a charged-page element on every page of the site
Views, controls, inputs12 views of one element, 56 kinds of control, 11 ways data comes in, 9 ways it goes out
Contracts14, listed below; the two that other sites and agents already program against are the reading-list link and articles/ids.json
Tests518 check calls in three files (loops make more checks at run time), now run in CI before a tag (R11)
Pages with a Content-Security-Policy0 (R10)
Upstreamstwo: sgit.ai for the account pages, subscribe, the contact file and the meter to 1.3.1, rewritten on import to this site's 1.4.0 (R12)

Where the reader’s data is kept

One key in this origin’s local storage, sgit.meter.v1, holds all of it; a session key holds the charge per path so a reload does not charge twice. Keys for the share and the subscription exist only in memory while the page encrypts. There is no cookie and no server-side store.

Each finding has its evidence and, where it is a bug, a test in admin/build/test_review.mjs that passes while the behaviour stays as it is, so that the fix is a visible change to the test. Severity is for a reader’s money or data first, the move second. Nothing here was changed in the code, by the brief’s rule: no behaviour changes until phase five. What the move takes from here

  • The before-hashes in the file and page tables, to be compared with the live site after the move with the same normalisation.
  • The controls and inputs tables as the checklist for the browser tests in three engines, and for the adversarial exercise: change what a reader sees or pays without a test failing.
  • The contracts table as the README of the new repository: these are the things that must not change in a pure refactoring.
  • The findings, one issue each, labelled with the phase they belong to; R10 and R12 are the shape of the work, the rest are its first items.
