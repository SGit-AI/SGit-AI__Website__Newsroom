What changed in this version {#corrections}

I asked the team that builds the sgit CLI to review this article and measure more. They found three things I got wrong, and this site's agent checked each one before changing anything:

• "Objects cache for a year at a CDN" was overstated. The server does send cache-control: public, max-age=31536000, immutable on objects. But reading the same object three times in a row came back x-cache: Miss from cloudfront every time, for the CLI team and again for this site's agent: the CDN in front of the API does not serve object reads from cache today. What is true, and more interesting, is below: objects can be kept for ever by anyone who fetched them, because their name says so.

• The 59-second clone was a bug, not sgit. The small vault's objects were requested in batches of 50, two of the responses were over the size limit of the Lambda that serves the API, and the client retried each batch through 14 seconds of back-off and then read the objects one at a time. The CLI's development branch now splits a refused batch in two. This site's agent re-ran the same clone: 51 and 58 seconds with the released CLI, 12.3 and 10.4 seconds with the fix, the same 106 objects.

• Dates and details. On-demand clones (--sparse) have existed since May; 0.18.0, on 7 October, added --path and --depth. The client sends batches of 50 objects, not 100 (the server's cap). The CLI team's earlier vault had 9,404 blobs, not files. And no packing on the server is not a gap: Scion has none either.

The first version is kept, as every version of every article here is.

2 unchanged paragraphs, under What Anthropic built {#scion}

The diagnosis is the interesting part. Git was designed for people working offline on full copies, and the post says that design "was actively undermining our ability to scale as the repo grew", because nearly all its clients are now agents and jobs that are always online. So Scion inverts it. The server keeps history and does blame, commits, merges and rebases; a unit of work is a changeset written server-side; refs move by a compare-and-swap on one database row; clients fetch only the trees and filesblobs they need, and many jobs never check out at all, but query an API. Objects are immutable, so three tiers of cache, per machine, per region and the authoritative server,cache each serve more than 99% of reads. Nowhere, not even on the server,"There is thereno a full copyequivalent of thepackfiles repository.(git's compressed bundles of objects), so no repository maintenance is needed." Directories can carry their own permissions.

The results, by the company's own figures: about 200 times less CPU and memory than the Git mirrors it replaced, checkouts in seconds instead of minutes, a quarter of CI's CPU given back, and a migration done in five months by seven engineers while merges grew tenfold, with Claude writing much of the code.engineers. The post is equally clear about what Scion is not: internal, and "by no means a suitable replacement for git for general use".

1 unchanged paragraph, under Why I recognised it {#recognised}

sgit started from the same instruction Anthropic arrived at: Git solved most of the hard problems, so copy Git. Commits, trees, blobs, refs and branches, with encryption on top, and a server that, in the words of the March brief, is "a dumb key-value blob store" while "All intelligence lives in the client." Reading Scion's post, the overlap is not in the architecture's centre of gravity, which is the opposite, but in the properties that make agents fast.

[figure sq-matrix.webp] Scion, sgit 0.22.0 and Git side by side: who does the work, encryption, object ids, partial copies, reads without the server, writes, merge, history queries, proven scale and availability. | comparison

Immutable identifiers that cache. Every object in an sgit vault is named by the SHA-256 of its ciphertext, so its name can never point at different bytes; the client checks every object against its name before using it. That is exactly the property Scion's cache tiers rest on, and the live server already uses it: an object read from the SG/Send service comes back with cache-control: public, max-age=31536000, immutable, through a CDN. Unchanged folders keep the same tree ids across commits, so they are not fetched twice.

Fetch only what you need. Scion's clients request only the trees and blobs a job needs. sgit 0.18 to 0.22 added the same family of options: --path for a scoped clone, in which "Other folders are carried by id and never downloaded", --depth for a shallow one, and --sparse for structure first and content on demand. The CLI team measured a scoped clone of one folder in 14 seconds against 81 for the full clone on a vault of 626 commits and 9,404 files; this site's agent measured the same pattern below.

Reads without the server. Scion keeps its server for reads, behind caches. sgit can do without one: because the objects are encrypted and immutable, a read is a plain GET of a known path, and 0.22.0's clone --transport static reads from "any GET host". The server only matters for writes, which go through a batch endpoint, up to 100 operations at a time, with refs moved by compare-and-swap, the same primitive Scion uses on its database row.

A server that cannot see. This is where sgit goes beyond Scion's post, which does not mention encryption. Files, file names, trees, commit messages and refs are all encrypted on the client. The server holds ciphertext, so it can be cheap, simple and anyone's: a cloud bucket, a CDN, a folder on a laptop. That is why the hosting is so simple; the server has nothing to protect and nothing to compute.

Measured on 0.22.0 {#measured}

[figure sq-bench.webp] One vault, five ways: a full clone in 58.6 seconds holding 12,664 KB of encrypted objects; depth 1 in 60.7 seconds; a scoped clone of one folder in 4.2 seconds and 412 KB; an on-demand clone in 3.6 seconds and 180 KB; and a full clone from a plain static file server in 1.6 seconds. | comparison

The agent installed sgit-ai 0.22.0, released on 15 October, and cloned a real published vault, the newsroom's synthetic-users vault of 83 files and 12 MB, with its public read key, twice in each mode. A full clone took about 59 seconds. A scoped clone of one folder took about 4 seconds and held 412 KB of encrypted objects instead of 12,664. An on-demand clone took 3.6 seconds and held 180 KB, the structure only. A shallow clone of depth 1 saved nothing on this vault, because almost all of its bytes are in the latest files; depth helps on long histories, not on young vaults.

Then the agent laid the same encrypted objects out as plain files and served them with Python's built-in file server, a program that knows nothing about sgit, and cloned from it with --transport static. The clone took 1.6 seconds on the same machine and was identical, file for file, to the clone from the API. It shows the mechanism rather than network speed, but it is the point: an sgit vault can be read from any storage that answers a GET, with no sgit server in the path.

[figure sq-matrix-v2.webp] Scion, sgit and Git side by side, revised: who does the work, whether the server holds plaintext, how a folder is protected, object ids, packing, partial copies, reads without the server, writes, merge, history, implementations, deployment, proven scale and availability. | comparison

Fetch only what you need, the same way. Scion's post: "Scion's negotiation doesn't tell the server what the client already has; instead, it operates exclusively on trees and blobs the client wants. Starting from a root tree, the client checks its local store for missing trees and requests them recursively, then repeats the process for blobs." That is sgit's clone and pull walk: level by level over the trees, then the blobs in batches of 50 with 16 requests in flight. A scoped clone asks only for the spine down to its folders, and an unchanged folder keeps its tree id across commits, so it is never fetched twice.

Immutable objects, kept by whoever fetched them. Scion: "Every request is for a specific object that never changes, so any cache can answer it." Every sgit object is named by the SHA-256 of its ciphertext, and the client checks each one against its name. The name also says what it is: immutable objects carry -imm-, the two mutable pointers carry -muw-. So a browser, a proxy, a CI cache or a folder can keep an object for ever by looking at its name, without reading it. That is how sgit.ai's own documentation pages, which are a vault read in the browser, load: 18 objects cold, then one 69-byte ref, then nothing inside a two-minute window. The trade is deliberate: no deltas between versions, so a changed file is a new object.

No packfiles, no maintenance. Neither system packs objects on the server, and both treat that as a feature.

Compare-and-swap. Scion moves a ref with a compare-and-swap on one row; sgit moves the ref and the branch index the same way.

Where they differ, sharply. Scion protects directories with permissions on a server that holds plaintext. sgit protects them with keys: one vault per trust domain, a read key that cannot be turned into a write key, and append lanes that can write without reading. Files, names, trees, commit messages and refs are all encrypted on the client, so the server has nothing to protect and nothing to compute, and it can be anyone's. More on that in sgit is a standard, not a server.

Measured on a real, busy vault {#measured}

[figure sq-bench-v2.webp] The measurements now: the 83-file vault this article first measured, 59 seconds with sgit 0.22.0 and about 11 with the fix, 4 seconds for one folder, 1.6 from a plain static host; and the 35,000-object vault the newsroom's agents share, 210 seconds in full, 57 with one commit of history, 13 for one folder with one commit. | comparison

The first version measured an 83-file vault, which says little about Scion's question: what happens when the repository is big and the clients are many. The right vault was close at hand: the one the agents behind this newsroom share every day, with their mail, briefs, runs and analysis. On 16 October it had 1,295 commits, 5,281 files and about 35,000 encrypted objects, 527 MB with all its history, which is the size of a real application's source repository.

A full clone is the worst case: three and a half minutes for 35,423 objects. But no agent takes one. With one commit of history, the whole tree is 57 seconds; one 130-file folder with one commit is 13 seconds and 3 MB, 137 objects, however large the vault is. A file fetched on demand is under 3 seconds; an up-to-date pull is 2.5. The full picture, with the honest edges, is in One vault, ten agents, measured.

And the time is the distance to the storage, not sgit. The same objects on local disk: the one-folder clone takes 0.8 seconds against a local API server, the full clone 69. On the small vault, the same encrypted files served by Python's built-in file server, with no sgit server at all, cloned in 1.6 seconds, identical file for file.

1 unchanged paragraph, under What it means {#means}

I find it fascinating to watch the same idea arrive twice. Agents change what source control is for: the clients are always online, the volume is machine-scale, and the expensive thing is moving bytes nobody needs. Anthropic answered inside one trusted company, with a powerful server that does the work. sgit answers for everyone else, where the server should not be trusted at all: encrypt everything on the client, name every object by its ciphertext, let any cache or bucket serve the reads, and keep the server dumb enough that anyone can run it. The two designs meet in the middle on immutable objects, partial fetches and compare-and-swap.

The practical difference is availability. Scion is a blog post. sgit is pip install sgit-ai today, with its code in the open, and it already carries the vaults this site publishes. The useful next steps are clear from Scion's list: server-side history queries that do not need the plaintext, blame and bisect, and testing at a much larger scale. Anthropic says it wants to share its ideas with Git platforms and the open-source community. The ideas that do not depend on a trusted server are already there.

Scion's post concedes one point from the other side: it could not keep a merge queue at its rate, so "concurrent changes can conflict, but Claude can typically fix these conflicts". The merge went back to the agent. That is where sgit keeps it: a merge is a workflow step, made where the context and the policy are.
