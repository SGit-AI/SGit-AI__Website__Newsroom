What sgit does that Git does not: what changed in v1.2.0

1 unchanged paragraph

Summary: Between 3 and 27 October, sgit shipped ten releases, and each one fixed a bottleneck that a real workload had found. A one-file commit on a 76,000-file vault went from 29 minutes to 4.6 seconds; a pull of a 300-file pass on 228,000 files from 566 to 31.7 seconds; a one-folder clone of a pack vault from 36 to 2.8 seconds. The ideas came from earlier work of mine: MGraph-DB's cross-references, Memory-FS's reads by offset, caching on content addresses, and the rule that the writer pays. It is time to stop describing sgit as "like Git". This is the map of what sgit does that Git does not, what Git also has, where Git is ahead today and how little of that is out of reach, and what is designed but not yet shipped. On 28 October sgit-ai 0.27.0 closed six of the eighteen rows where Git was ahead, line-level merges, partial commits, signing with your own key, rename detection, blame and grep, each checked against Git's own output. The sgit CLI team reviewed itthis article against their code, and it is corrected and extended from their review.

Where Git is ahead today, and how much of it can be built {#git-ahead}

These are real gaps, and most are minor or mid-level for the way we use sgit: workflows that are not common for agents writing documents and data. Almost everything here runs on the client in Git too, on plaintext the client already has, so it can be built in sgit the same way. The CLI team's review sketches how for each one.

• Merges. Git merges line by line and detects renames; sgit merges whole files and writes a conflict file. A line-level three-way merge on the client is the biggest visible gap, and a medium-sized job.

• Hunk-level staging. Named files, yes (sgit write); parts of a file, no.

• Who may write. GitHub knows who pushed, protects branches per person, and its signing keys expire and can be revoked. A signature in sgit today proves that some key holder wrote a commit, not which clone, and there is no per-key expiry, only rotating the whole vault. An owner-signed list of allowed signers is designed.

• Storage. Git has delta packs and garbage collection. sgit has neither yet; for pack vaults, pack compact moves superseded packs to an archive, which is part of the answer. Git's ids are 160-bit by default; sgit's format 1 is 48-bit, and format 2, 128-bit, is opt-in per vault.

• Tools. Blame, bisect, grep over content, IDE support, review and CI. All but the hosted parts are client-side in Git too.

Where Git is ahead, and how fast the gap is closing {#git-ahead}

These were real gaps when I wrote the first version of this map, and most of them were minor or mid-level for the way we use sgit. Almost everything Git is ahead on runs on the client in Git too, on plaintext the client already has, so sgit can build it the same way. The CLI team wrote a Git-parity roadmap on 28 October, with Git the client as the bar and every new feature off by default, and released the first part of it the same day.

[figure sf-parity.webp] Six of Git's eighteen leads closed in sgit-ai 0.27.0, each checked against Git, and the twelve still open. | comparison

Closed in sgit-ai 0.27.0, 28 October, each checked by the CLI's build agent against Git's own output:

• Line-level merges. pull --merge lines and branch merge --merge lines, with Git's conflict markers; opt-in, with the whole-file .conflict still the default. 4,500 random merges were byte-identical to git merge-file.

• Partial commits. commit with paths, commit -p, and --list-hunks and --hunk for agents.

• Signing with your own key. commit -S, signed tags, merges and reverts, with SSH or OpenPGP keys, verified against the allowed signers in your Git configuration. It is a second signature beside the clone's own.

• Rename detection, a port of Git's: 90 of 90 pairs equal git diff -M --name-status.

• Blame: 25 of 25 files equal git blame --porcelain.

• Grep and the pickaxe. sgit grep over the working copy or any revision, decrypted in memory, and log -S and -G: 120 of 120 grep runs equal git grep.

Still ahead, by how firm the plan is:

• Designed and next in the CLI team's queue, about 21 days of work in all: cherry-pick, built on the line merge; local hooks that never sync; rebase, never rewriting pushed history; bisect; and worktrees.

• Waiting on another team or the server: reading one file from a pack vault with no clone, and a command for append lanes.

• Sketched, built when a workload asks: garbage collection, delta compression, and archive, shortlog, describe and aliases.

• No working plan yet: per-folder read access, which needs per-folder keys, and submodules.

• Who may write. GitHub knows who pushed, protects branches per person, and expires and revokes its signing keys. A signature with your own key now says which person signed, when you verify it against your allowed signers; accounts, protected branches and an owner-signed list of who may write are moved to a future server the roadmap calls SGitHub, with review and CI.
