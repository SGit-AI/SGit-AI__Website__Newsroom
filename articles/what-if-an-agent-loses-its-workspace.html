What if an agent loses its workspace? Mondweep Chakravorty's SGit × Ruflo proof of concept, step by step: memory saved encrypted, the project deleted, the memory back in a fresh process, and three safeguards that held

By Dinis Cruz · 2026-10-17 · article v1.1.0, 2 versions · newsroom v0.12.90 · agentsruflosgitvaultsagent-behaviour-policymcpmemoryrecoveryvideoarticle

Abstract: Mondweep Chakravorty has made a short video that answers a question every team running agents should ask: if an agent loses its workspace, does its memory come back, and do its written permissions still hold? In 104.7 seconds it replays a real terminal run in twelve steps. Ruflo, rUv's open-source agent orchestration, stores two facts in its memory. An adapter governed by an Agent Behaviour Policy saves that memory as an encrypted checkpoint made of SGit objects. The original project is deleted. A brand-new process restores the checkpoint, the restored database has the same SHA-256 fingerprint as the one saved, and Ruflo reads both facts back word for word. Along the way three safeguards are tested and hold: a request outside the agent's permission is refused, a deletion that needs approval is stopped, and a tampered checkpoint is rejected. The video is careful about its limits: recall by meaning was not validated. The code is public too, MIT, with 16 tests and recorded evidence, and its runner has since also validated keyword recall against Ruflo's real memory store. This is the first of three pieces on it, with a page that lets you step through the run yourself.

In short

  • The question. If an agent loses its workspace, does its memory come back, and do its permissions still hold?
  • The answer, on screen. Both facts came back exactly, in a fresh process, after the original was deleted.
  • The fingerprint matched. The restored database has the same SHA-256 as the one saved.
  • Three safeguards held. Out of scope refused, deletion without approval stopped, tampered copy rejected.
  • It says what it did not test. Recall by meaning was switched off and is marked not validated.
  • It is a real run, and the code is public. Ruflo and SGit pinned; 16 tests; the evidence is in the repository.
  • Step through it yourself. Every step has a page with its frame, command, output and diagram.

The question

Agents keep memory: facts they were told, decisions they made, what they found. That memory usually lives in a file in the agent's workspace. So what happens when the workspace goes, a container recycled, a disk wiped, a project deleted by mistake? Does the memory come back, and does it come back with the rules the agent was working under?

Mondweep Chakravorty, a member of the #Ruflo-Federation and co-founder of the Agentics Foundation's London chapter, made a video that answers it with a real run: SGit × Ruflo | Working Proof of Concept, published on YouTube on 17 October 2026. It is 104.7 seconds long. Each slide has the story on the left, for someone with no code knowledge, and the terminal on the right, labelled as an actual capture of the run.

His code is public at mondweep/sgit-ruv-memory, under the MIT licence: a local MCP server of four tools, a strict compiler that turns an Agent Behaviour Policy into Ruflo rules, 16 tests, and the evidence from each run. The analysis behind this piece was made from what is on screen, frame by frame, in a separate session with Claude, and then checked against that code. Every number below comes from the video's timeline, a frame or the repository. If you would rather click than read, step through it here.

The run, in twelve steps

1 · A real, pinned runtime

At 0:09, ruflo --version returns v3.56.10, and the run prints the SGit source commit it uses, 559752641bc5…6ad0d4ad, and the adapter: an ABP-governed local MCP server, version 0.2. Pinning the versions is what makes a run like this reproducible. Step 1, in detail.

2 · Define the mandate

At 0:14, four Agent Behaviour Policy rows, all scoped to the project: write memory, yes; read memory, yes; read history, yes; delete memory, approval. And one line that matters more than it looks: "No raw rule overrides. Unsupported or ambiguous policies fail closed." That is an Agent Behaviour Policy in miniature: what the agent may do, and where a person has to step in. In the code, the rows are compiled into Ruflo rules when the server starts, and every tool call is checked by a pinned copy of Ruflo's own policy evaluator, in enforce mode. Step 2.

3 · Store two facts through Ruflo

At 0:21, Ruflo's own command line stores two synthetic facts, with embeddings switched off: "Kestrel vehicles may charge only between 01:00 and 04:00 UTC", and "Kestrel checkpoints are retained for seven days". The terminal reports "[OK] Data stored successfully". Step 3.

4 · Try something outside its permission

At 0:32, the run asks the adapter to checkpoint a namespace called forbidden. It is refused with a PermissionError, and checkpoint_files is 0: nothing was written. Step 4.

5 · Save an encrypted recovery point

At 0:38, the checkpoint for the project namespace is allowed. The adapter takes a consistent copy of the memory database, a SQLite backup rather than a raw file copy, and records three fingerprints: of the database, of the ABP and of the compiled policy. The screen says: "Only encrypted SGit bare objects enter the checkpoint store. Private keys remain in a separate private directory." Binding the data to the rules in force is the detail I like most. Step 5.

6 · Approval means stop

At 0:45, the run tries to close the run, which would delete memory. That row says approval, and none is supplied, so it stops with a PermissionError and checkpoint_retained: true. Step 6.

7 · Remove the original workspace

At 0:51, the disposable test project is deleted: source_project_exists: false, original_database_exists: false. The loss is real, not simulated. Step 7.

8 · Restore in a fresh process

At 0:58, a brand-new MCP server process restores the checkpoint into a workspace called fresh-runner. The database's SHA-256 begins 10ab6c56 and ends d66a0b, the same as in step 5, and matches_checkpoint is true. Step 8.

9 · Ask Ruflo what it remembers

At 1:04, Ruflo itself, not the adapter, reads the restored memory. Both facts come back word for word: "PASS: both values match the CLI-written facts exactly." That the original tool does the reading is what makes this proof stronger than a demo that checks its own output. Step 9.

10 · A missing fact stays missing

At 1:14, a key that was never stored is looked up: "Key not found: never-stored", exit 1. The restore did not invent anything, and the check can fail. Step 10.

11 · Change the saved copy, try again

At 1:20, one encrypted checkpoint object is altered and a restore is tried into a workspace called tampered. It fails with a ValueError, and tampered_workspace_created is false. Integrity fails closed. The code shows how: the adapter compares the digest of the stored ciphertext with the one it recorded when it saved the checkpoint, and refuses before anything is decrypted. Step 11.

12 · What this run proves

At 1:26, the acceptance summary: exact recall PASS 2/2; ABP denial PASS; deletion that needs approval BLOCKED, checkpoint retained; fresh-process restore PASS; tampered restore BLOCKED; and semantic recall NOT VALIDATED, because embeddings were off. Step 12.

What it proves, and what it says it does not

The video's own closing slide puts it well: both facts recovered exactly; unauthorised access blocked; unapproved deletion blocked; altered checkpoint rejected. And still to validate: recall by meaning, real-world value, and installation and ongoing reliability.

The repository adds one more result. Its acceptance runner stores two facts through Ruflo, checkpoints Ruflo's real .swarm/memory.db, removes the whole project, and reads the facts back in the restored workspace: exact values and keyword search result keys match before and after. Recall by meaning is reported as partial, because no vectors were stored even with embeddings on; the README names that as the next investigation.

What makes it more than a demo is the shape of the loop. Most "memory that persists" demos skip the deletion or reuse the same process. This one stores, saves, deletes for real, restores in a new process, and reads back with the original tool. It also tests the refusals, not only the happy path, and includes a negative control. And it is honest about scope, in the run itself, not in a footnote.

Why it matters to me

This is the first time someone outside our own sessions has taken the two ideas we keep arguing for, an encrypted vault as an agent's memory and a behaviour policy beside the prompt, and run them together inside someone else's agent stack, on camera. It is exactly the combination Agentics, ready to sell describes as the product: a hive, a memory and a mandate. Mondweep is one of the two people that piece names to deliver it.

Where to go next

The run raises two questions this piece does not answer. When is the vault actually used? In twelve steps it is written or read in three, on one machine, inside the adapter: the architecture piece explains why that is the honest answer. Is every path to the memory guarded? Ruflo's own command line reaches the memory file without the policy: the third piece asks what that means. Or step through the run, with every frame, command and diagram.

What this does not claim

  • From the screen and the code. The audio was not transcribed; the code was read, not run, by this site.
  • A proof of concept, not a product. The video says so; reliability and real-world value are still to validate.
  • Recall by meaning was not tested. Exact recall was.
  • The facts are synthetic. Kestrel is a test name, not a real fleet.
  • The analysis is an AI's, reviewed here. It was made by Claude for me and checked against the frames by this site's agent.
