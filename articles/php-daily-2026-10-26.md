- **Still no confirmed victim.** Five days in, 543 sources, and no named organisation says it was compromised.
- **The advice is shifting:** from "install the fix" to "and check whether you were already broken into".
- **A bounty was won.** It proves the flaw gives full control; the target was built to be attacked.
- **One repository became six,** split by who writes and how often.
- **Releases in seconds:** 25 to 42 seconds from push to live, instead of a median of 88.
- **The old repository is frozen,** and the main address now serves the new build.

- **Not done yet:** the pages still wait on one build, and on a token only I can set.

## The story

The line that matters has not moved. As the site's [evidence on compromise](https://php.oct.2026.newsroom.sgit.ai/compromise/index.html) puts it, at its check of 14:42 UTC on 26 October: "No named organisation has said it was compromised through php2shell." It is marked as what it is, "a time-bounded absence, not a confirmed fact", and one statement from one organisation would end it.

- **More evidence, same answer.** The evidence vault grew from 382 sources at update 3 to 543, with 605 captures. The researcher's source watch now follows 1,273 pages from 934 publishers.
- **The advice is changing.** The front page now says it plainly: the advice "is moving from 'install the fix' to 'and check whether you were already broken into'", with Singapore's and Luxembourg's authorities saying so.
- **A reader's question, answered.** The chief correspondent wrote [Has anyone actually been hacked through php2shell?](https://php.oct.2026.newsroom.sgit.ai/articles/has-anyone-been-hacked/index.html) from 525 sources: millions of attack attempts, several vendors saying "exploited in the wild", websites pulled offline as a precaution, and not one organisation that has said it was broken into.
- **A won bounty is not a victim.** The same group of readers asked about [a "steal my bitcoin" challenge](https://php.oct.2026.newsroom.sgit.ai/articles/steal-my-bitcoin/index.html): a server built on purpose to be vulnerable, with about $2,000 of bitcoin on it, which a researcher broke into on 25 October and wrote up. The correspondent's reading: "real proof the flaw gives an attacker full control of a machine", and "a game with a consenting target, not a victim". It ran PHP 8.4.26, one release below the fix, using PHP's own built-in web server, a mode not meant for production.
- **One name to check.** At 16:26 UTC the journalist recorded a secondary report that Square Enix confirmed unauthorised access to its systems that week, which does not say it was through PHP, next to another report that it took servers offline as a precaution because of the flaws. It went in as unverified, with the cause not stated, and the journalist left the headline line for the correspondent to decide. That is the review stage doing its job.
- **The third flaw,** CVE-2026-115560, is as update 3 described it: it affects fully patched releases, needs a rare setting, and has the mitigation `session.upload_progress.enabled=0`. No exploitation of it is reported.

The journalist's [state of affairs](https://updates.php.oct.2026.newsroom.sgit.ai/views/state/v3/index.html) is still version 3; version 4 waits for the new build. That is the other story of these two days.

## One repository into six

One repository into six, as split on 25 October 2026: press, data, team and the three page sites.

By 25 October the site had outgrown its repository. Dev's [proposal](https://team.php.oct.2026.newsroom.sgit.ai/admin/briefs/2026-10-25__proposal__one-repository-into-six/index.html), measured at noon that day, counted 3,332 files, 1,057 pages built by one build script of 7,847 lines, 77 releases on 24 October alone, and 28 release messages in three days naming a conflict, a collision or a renumbering. Every release rewrote about 1,900 files, because the version is stamped on every page, and every release paid for the full gate, 74 seconds, whether it was a redesign or one run record. Its diagnosis is the useful part: "The cause is not the number of agents. It is that one version, one build, one gate, one board file and one output tree serve everything."

So we split it along who writes and how often, not along technology:

- **press:** the build library, the gate, the release scripts and the shared assets. Dev writes it; security reviews every change.
- **data:** the API. The evidence exported from the vaults, the claims, the timeline, the state of affairs, the risk graph, the ontology. Every version is immutable once published, with a manifest of every file's sha256.
- **site:** the main pages, the briefings, the questions, the stories and the tools.
- **refs:** a page per source and capture.
- **updates:** the state of affairs, the desk, what is new, the feeds.
- **team:** the board, the schedule cards, the run records, the briefs, the control room, and every agent's own folder.

The repositories meet only through published, versioned addresses, never through a shared file, and a site pins the data and press versions it was built with. I created the six repositories between 15:31 and 15:34 UTC on 25 October; by 18:12 UTC all six were serving, and every old address on the site still answers.

## What the split buys

What the split buys, measured by dev on 25 October 2026: CI runs, the gate step, files per release and a check.

[The first day's report](https://team.php.oct.2026.newsroom.sgit.ai/admin/briefs/2026-10-25__report__one-repository-into-six-the-first-day/index.html) measured it. A CI run from push to live took a median of 88 seconds in the one repository, and 25 to 42 seconds in each of the six. The gate step went from 70 to 132 seconds to between 0.1 seconds, for the team's records, and 7 seconds, for the references. In the report's words: "A change to the references is checked in 7 seconds instead of 75, and a change to the team's records in a tenth of a second."

That matters more than it sounds. A run record used to cost an agent 2 to 4 minutes and a fight over the one board file; three of dev's own releases on 25 October were stopped by another agent's board write. Now it is one file in team, checked in a tenth of a second.

The split was also reviewed, the same evening, by the design agent, [from the outside](https://team.php.oct.2026.newsroom.sgit.ai/admin/briefs/2026-10-25__review__the-split-as-served/index.html). Its verdict was fair: "a separation of serving and proofing, not yet of making". Every page was still made by the old build. And it found a problem the one site never had: a reader is a stranger on every host, so a reader who chose Security on the main site was greeted as a first-time Executive on the references, with a new wallet for the reading meter on each.

## The cutover

The data host, data.php.oct.2026.newsroom.sgit.ai, at version 0.1.39, with every version immutable at its own address.

On 26 October the old repository was frozen at v0.22.22, in two steps, so that nothing depends on it any more: the build now runs in a box made from the six. Since then the data host has gone from version 0.1.12 to 0.1.39, and the press from 1.0.0 to 1.0.41 since it started on 25 October. At 16:30 UTC the press switched the main address, and edition v0.22.32, at 17:07 UTC, is the first served by the new build at [php.oct.2026.newsroom.sgit.ai](https://php.oct.2026.newsroom.sgit.ai/), with its robots file open to search engines and its own sitemap.

The design moved with it. Every page now carries "the line", one band under the masthead that talks to the reader as the persona they chose, Executive by default, with six others a click away. Views live in the address, such as `/agencies/as/security/`, a path that is not a file: the site's `404.html` reads it, loads the real page and shapes it in the browser. The real pages stay the same for every visitor and every crawler, so only they are indexed.

## The agents' tools got faster

sgit 0.25.0 in the newsroom, measured by the researcher on its source watch vault on 26 October 2026.

On 26 October every agent moved to sgit 0.25.0, after the newsroom reported how slow the source watch vault had become, at 79,465 files and 2.7 GB. The researcher's first full pass on it, at 09:34 UTC, [measured the difference](https://team.php.oct.2026.newsroom.sgit.ai/admin/briefs/2026-10-26__brief__for-the-sgit-cli-team-0-25-0-in-the-newsroom/index.html): the first commit took 25 seconds instead of 12 minutes 38, the push 67 seconds instead of 4 minutes 16, the data export 34 seconds instead of 9 minutes, and the whole pass 35 minutes instead of 57, with nothing lost.

The same brief is honest about what is still slow. The curator's first `status` after the upgrade took 18 minutes 23 seconds, of which only about a minute was work, and a `pull` of two passes took 25 minutes. Its conclusion, sent back to the sgit team: "pull is now the slow step". That is how these tools improve: the newsroom is a demanding user, and it reports with numbers.

## A new write needs a proposal

The curator's wakes are light, and it asked, with the journalist, whether it should write the data files that come from its own promotions. [My decision](https://team.php.oct.2026.newsroom.sgit.ai/admin/briefs/2026-10-26__decision__the-curator-writes-data/index.html), recorded by the conductor at 14:34 UTC, set a rule for any agent taking on a new write: a documented reason, a review by the agents it touches, agreement, then a trial, with the run records showing how it went.

The curator filed its proposal at 15:52 UTC. In its session I then told it to start, since several agents watch the vaults and a few mistakes while we find the workflow are acceptable; it released its first data files at 16:14 UTC, with 543 sources and 605 captures, and the review open. The journalist replied "yes", and noted that its own export of the same vault head had produced identical bytes, so the two releases merged with no conflict. That is a good first test.

## Every release live again

The control room at edition v0.22.32, with the pipeline from researcher to desk and the agents flagged.

The split has a cost we are still paying. In the old repository, every agent's release built and deployed the live site itself, within minutes. After the split, the pages are made by one build, the press chain, which runs only when dev runs it. On the morning of 26 October nothing the agents had released since 01:43 UTC was on the pages. So the conductor wrote, at my direction, [a requirement](https://team.php.oct.2026.newsroom.sgit.ai/admin/briefs/2026-10-26__brief__every-release-is-live-again/index.html): "Parity with v1." An agent that releases its own repository must be live, in its own area, within minutes, with no hand-run step by anyone else.

Dev has built the first half: a workflow in the press that runs the chain every quarter hour and builds only when one of the six has changed. It waits on one thing, a token only I can set. Until then, editions are made by hand: v0.22.28 at 11:38 UTC, then nothing on the pages until v0.22.29 at 16:01. The second half, "pass two", gives each site its own build from its own sources, so the press serves only the shared assets.

## What waits on me

The [control room](https://team.php.oct.2026.newsroom.sgit.ai/team/control/index.html) counts it: 17 items waiting on me, 4 decisions, 2 agents blocked, 16 branches ahead with 43 commits. The four decisions, in the conductor's words, start with the obvious one: "Set ROUND_TOKEN", without which "nothing released today reaches the pages". Then security's review of the new release steps, whether wakes write the data files (now answered, for the curator), and how dev's daily wake should run. The team's status data lists 23 agents, and their sessions' running totals add up to $1,025, up from $928 at update 3.

The lesson of updates 2 and 3 still holds. The agents are fast, and the decisions are mine. The split makes the agents faster still, so the queue for my decisions gets longer, not shorter.
