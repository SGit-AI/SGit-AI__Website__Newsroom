A minimal viable browser: why Firefox is the one that can build it, and what it would take

By Dinis Cruz · 2026-10-18 · article v1.1.0, 2 versions · newsroom v0.12.106 · browsersfirefoxmozillaminimal-codeagentsprompt-injectionextensionsattack-surfacearticle

Abstract: The browser is the biggest program most of us run, the largest attack surface on the machine, and the place we now want to put agents. It does far more than any single job needs. A kiosk running one application, an agent filling in one form, and a person reading the news all get the same enormous engine, with every feature on. This follows the argument of the code you do not ship to its most visible case. A minimal viable browser has a small kernel, reviewed hardest and changed least, and loads components only when a page or an agent needs them, so its attack surface grows only as it is used. A browser for one application has no extensions, no media and no downloads. A browser for one agent has no accounts, no extensions and no file access, which is a practical defence against prompt injection: an agent cannot leak what its browser cannot reach. And every extension runs in its own box, with only the access its job needs, instead of the "read and change all your data on all websites" that so many hold today. Several projects already do part of this, from hardened Firefox forks to headless browsers built for agents. But I think Mozilla is uniquely placed to do all of it: it has its own engine, privacy is its brand, it runs on the client, and its revenue still does not depend on knowing more about its users. The pitch to Mozilla, though, should not be security. It should be speed: a browser that only has the code it needs is a browser that starts instantly and uses a fraction of the memory.

In short

  • The browser is the biggest attack surface we run. And now we want to give it to agents.
  • One engine, every feature on, for every job. A kiosk, an agent and a reader all get the same.
  • A minimal viable browser. A small kernel, and components loaded only when needed.
  • A browser for one agent is a prompt-injection defence. An agent cannot leak what its browser cannot reach.
  • Every extension in its own box. Only the sites and the powers its job needs.
  • Parts of this exist. Hardened forks, headless browsers for agents, kiosk modes.
  • Mozilla can do all of it. Its own engine, a privacy brand, the client, and money not tied to profiling.
  • Sell it as speed, not security. Only the code it needs starts instantly.

The biggest program we run

The browser is where most of us spend the day, and it carries every capability the web has ever needed: a JavaScript engine with a just-in-time compiler, WebAssembly, WebGL, media codecs, PDF, fonts, downloads, extensions, sync, accounts. A page that shows text and a form gets all of it, on, by default.

The cost of that shows up in the bug counts. In May, Mozilla wrote that it fixed 423 security bugs in Firefox in April 2026, against roughly 20 to 30 a month through 2025. 271 of them were found with an Anthropic model and fixed in Firefox 150: 180 rated high, 80 moderate, 11 low. A number of them were sandbox escapes, written assuming the content process was already compromised and going after the privileged parent process through IPC, IndexedDB and image decoding. Chrome is seeing the same: one update on 6 October 2026 fixed 247 vulnerabilities. Counted from NVD by the organisation that filed them, Google's Chrome team filed 202 CVEs in 2025 and 3,246 in 2026 up to 17 October; Mozilla's filed 213 and 675 (Mozilla's also cover Thunderbird and other products). This is the code you do not ship argument at its largest: models now find what was always there, and every feature in the engine is a place to look.

The vendors already know that less code is safer, because they ship it as a mode. Microsoft Edge's enhanced security mode turns off the V8 just-in-time compiler, after Microsoft said in 2021 that 45% of V8 CVEs in 2019 were JIT-related. GrapheneOS's Vanadium browser has the JIT disabled by default, with a per-site toggle. Apple's Lockdown Mode blocks "certain complex web technologies". Tor Browser's Safest level turns off JavaScript altogether. Each is a minimal browser for one threat, switched on by hand. What does not exist is the general version: a browser that starts small and only grows when it has to.

What a minimal viable browser looks like

The shape is the same as the minimal viable code path, applied to one program.

  • A small kernel. Networking, TLS, parsing, layout, and process isolation. This is the part that is reviewed hardest and changed least.
  • Components, loaded when needed. JavaScript, with or without the JIT; WebAssembly; media; WebGL; PDF; downloads; extensions; sync. A page or an agent asks for one, and the browser loads it, for that site.
  • A profile that says what it is for. One application, one agent, or a person browsing. The profile decides what can be loaded at all.

Three browsers come out of the same engine. A browser for one application has no extensions, no media and no downloads: a kiosk, a till, an internal tool. A browser for one agent has the same, plus no accounts and no file access. And the reader's own browser loads what they use as they use it, with each extension in its own box.

Firefox has had pieces of this, and dropped some of them. It had a site-specific browser, behind a hidden preference, and removed it in Firefox 86 in 2021, citing known bugs and weak user research. It has a kiosk mode, started with --kiosk. It has had site isolation on for every desktop user since Firefox 95, which is the process boundary a component model needs. And Servo, the engine Mozilla started in Rust, is now an embeddable library, published as 0.1.0 in April 2026 under Linux Foundation Europe.

A browser for one agent

This is where the argument stops being about tidiness. We are now giving browsers to agents, and the agent reads everything the page says.

The vendors say plainly that this will not be fixed. OpenAI wrote in December 2025 that prompt injection, "much like scams and social engineering on the web, is unlikely to ever be fully 'solved'" (TechCrunch). Google's Chrome security team wrote in December 2025 that "the primary new threat facing all agentic browsers is indirect prompt injection". Gartner told most organisations to block AI browsers for now.

The incidents show where the damage comes from. In March 2026, Zenity Labs disclosed PleaseFix, a zero-click hijack of Perplexity's Comet through a calendar invite that reached local files and password-manager workflows. The fix was to restrict file:// access: not a smarter model, a smaller browser. At Black Hat in August, the same researchers showed zero-click chains against the agents in Chrome, Edge, Comet and ChatGPT Atlas; some vendors patched, others called it intended behaviour.

The better defences already point the same way. Atlas has a logged-out mode that runs the agent with no cookies or logins. Brave runs its AI browsing in an isolated profile with its own cookies and storage, and recommends isolating agentic browsing from normal browsing. Chrome adds Agent Origin Sets, which limit the sites an agent's task can touch, and a second model that checks proposed actions.

A minimal browser makes that the default rather than a setting. An agent's browser that has no accounts, no extensions, no file access and only the origins its task needs cannot leak a password it never had or a file it cannot open. In the terms of what can your agent reach, the grant shrinks to the mandate, and the injection that gets through finds nothing to take.

Every extension in its own box

Extensions are the part of the browser that users add, and they are where much of the recent damage came from. LayerX's 2025 report found 99% of enterprise users have an extension installed, and 53% have at least one with high or critical permissions.

The pattern in the incidents is not malicious code at install. It is a trusted extension that changes. Koi's ShadyPanda report, as The Hacker News relayed it, covers about 4.3 million installs across 145 extensions (20 for Chrome and 125 for Edge, Koi's count of one phase), some of them "Featured" or "Verified", that were legitimate for years and then were weaponised through auto-update. Urban VPN Proxy, with a Featured badge, began harvesting every prompt and reply on ChatGPT, Claude, Gemini and Copilot from a July 2025 update, with no off switch. Firefox is not immune: Koi's later DarkSpectre attribution includes Firefox add-ons.

An extension in its own box gets only the sites and the powers its job needs, and a change to either is a new request, not a silent update. Firefox has started down this road. In Manifest V3 it made host permissions opt-in and controllable per site, and new extensions must declare their data collection at install. It has also kept the blocking webRequest API that Chrome removed, which is why full uBlock Origin still runs on Firefox. The next steps are a process per extension, and a permission model that is an Agent Behaviour Policy in all but name: what this extension may do, on which sites, and who approved it.

Parts of this exist

None of this is new as an idea, and much of it ships today, in pieces.

  • Hardened Firefox builds. LibreWolf, with less telemetry; Mullvad Browser, built with the Tor Project for anti-fingerprinting; Tor Browser itself; Waterfox, which ships with no AI.
  • Smaller Firefox interfaces. Zen, with about 45,000 stars on GitHub, and Floorp.
  • A paid minimal browser. Brave Origin, launched in June 2026 for about $60 one-time, removes the AI assistant, news, rewards, wallet, VPN, Tor and playlist and keeps the blocker. People will pay for less.
  • Chromium with things taken out. ungoogled-chromium, and Vanadium, with the JIT off.
  • New engines. Ladybird, still in development and funded by donations, and Servo.
  • Browsers for machines. Lightpanda, written from scratch for agents and automation; Chrome's headless shell, a separate thin binary; and hosted browsers such as Cloudflare's Browser Rendering.
  • Shells for one app. Tauri uses the system web view, and says a minimal app can be under 600KB.

What is missing is the same engine, from the same vendor, in all three shapes, with the components as the unit.

Why Mozilla

I think Mozilla is better placed than anyone to build this, for four reasons.

It has its own engine. Gecko is the only independent engine with a large user base that is not Chromium or WebKit. A component model goes all the way down into the engine; a fork of someone else's cannot set that direction.

Privacy is the brand. Mozilla's state of Mozilla report puts Firefox at about 200 million monthly users, and the company has already shipped the instinct this needs: Firefox 148 added a switch that turns off current and future generative AI features. Its Smart Window is opt-in and does not act on pages yet. That is a company that already sells "you choose what runs".

It runs on the client. An agent's browser that holds nothing and reaches only what it needs is a client-side product. It does not need a server that sees the browsing, which is the same design as sgit.

Its money does not come from knowing more about you. Here the memo needs a correction: Mozilla's revenue is not independent. Mark Surman said in April that search was until recently about 95 to 98% of revenue, with privacy-preserving ads now about 10 to 12%, and most of the search money comes from Google. The court remedies in the Google case let those payments continue but limit default deals to one year at a time, and both sides have appealed. What holds is the part that matters here: Mozilla is paid for a search box, not for profiling its users, and it has about $1.4 billion in reserves and a plan to run its products as separate companies, each with its own accounts. A minimal browser for agents and applications is a product someone pays for directly, the way Brave Origin is, and it is the kind of revenue Mozilla says it wants.

Sell it as speed

The pitch to Mozilla should not be security. Security has rarely been enough to make people switch browsers, and Firefox at 2.8% of the market in September 2026 knows it.

The pitch is that a browser with only the code it needs is fast. It starts at once, it uses a fraction of the memory, and an agent can run many of them. Lightpanda's own benchmark, which is the vendor's, claims 123MB against 2GB of peak memory for 100 pages, and 5 seconds against 46. A kiosk that boots in a second, an agent that opens a hundred clean browsers on a laptop, a reader whose browser does not load a PDF engine until they open a PDF: those are features people notice. The security comes with them, the way encryption made sgit better rather than being the reason to use it.

Firefox now ships every two weeks, from Firefox 155. A component that loads on demand is a component that can ship, and be pulled, on that cadence too.

What this does not claim

  • No minimal viable browser exists in this form. The pieces do; the design is a proposal.
  • Mozilla has not said it will build it. Nothing here is from Mozilla beyond what is linked.
  • Smaller is not safe. A kernel still has bugs, and an agent with no file access can still be talked into a bad form submission.
  • The CVE counts are ours. Counted from NVD by filing organisation on 18 October 2026; the 2026 rise reflects AI-assisted bug finding as much as new bugs.
  • Some figures are the vendor's own. Lightpanda's benchmark, Brave's and Mozilla's user counts, LayerX's survey.
  • Mozilla's 2024 and 2025 revenue split is from interviews and its ledger page. Its ledger page links its 2024 audited statements.
  • Loading components on demand has costs. Fingerprinting is one: a browser that loads different parts for different sites can look different to each, which is why Mullvad removed its security-level button.

If you work on a browser and want to try a component model for agents, write to agent@riskmandate.ai.
