Your own newsroom: how a founder can tell their story by voice memo, with an agent that checks it and publishes it to GitHub Pages, and readers who pay a little if they find it useful

By Dinis Cruz · 2026-10-15 · article v1.2.0, 3 versions · newsroom v0.12.80 · newsroomreplicatevoice-memosgithub-pagesgithub-actionsclaude-codefounderssg-meterpaymentsclient-sidehow-toarticle

Abstract: The founders I most want to see succeed are the authentic ones, the people who come from the field they are building for. Their brand is themselves, and they need a medium for it: a place that keeps their history, what they do, their stories, their struggles, their ideas, their path and their milestones, so that they remember it and others can find it. This site is written that way. I record a voice memo, an agent session wired to GitHub researches it, checks every claim, writes it in my voice and publishes it to a static site, and readers pay a few pence a page if they find it useful. Everything needed to do the same exists today. This is the recipe, step by step: one public GitHub repository; GitHub Pages, published by GitHub Actions after a validation step; a Claude plan with cloud sessions and the Claude GitHub App, used from a browser or a phone; a house-rules file the agent reads first; the reader meter from api.newsroom.sgit.ai, pinned to a release, with a Stripe Payment Link you own; and the habits that make it trustworthy: corrections in the open, sources at the end, and nothing confidential in a public repository. It is simpler than this newsroom, and it does not need to be called a newsroom. It is also a good way to learn, in a native way, what publishing a pure client-side site actually means.

In short

  • An authentic founder's brand is their story. It needs a medium that keeps it.
  • The loop is short. Speak a memo; an agent researches, writes, checks and publishes; readers pay a little if it helps.
  • Everything needed exists today. GitHub, GitHub Pages, Claude cloud sessions, the reader meter, a Stripe Payment Link.
  • The house rules are the product. One file the agent reads first: your voice, what to check, what never to publish.
  • It is pure client-side. Static files on a free host; the reader's balance lives in the reader's browser.
  • A behaviour policy runs the agents. From the privileges they get to how often you publish and in what tone.
  • Writer, editor, publisher. Separate agents, separate grants, enforced by prompt or by hook.
  • A private vault beside the public site. Drafts, data and guidance stay encrypted; only the final text is published.
  • Honest about the gaps. The writing pipeline is a pattern to copy, not yet a kit.

Why a founder needs one

When you go into the whole entrepreneur flow, the thing that matters most for some founders is not the deck; it is that they are the real deal. The expert founders argued that the next generation of companies will be built by people who come from the field. For them, the brand is the founder: their authenticity is the proof.

That brand needs a medium. A founder has to remember their own history, and needs a way to capture what they do as they do it: the stories, the struggles, the ideas, the path, the milestones. Most of it is lost in calls and chats. A site written from voice memos keeps it, with dates, and because every claim is checked before it is published, it is a record that others can trust. I found out on this site that my own memory needs checking; a founder's does too, and it is better to find out before an investor does.

And there is a second reason. Building one teaches what a pure client-side site is: static files on a host, code that runs in the reader's browser, and no server that holds anyone's data. For a founder moving their own product in that direction, publishing their story this way is the most native way to learn it.

What you need

  • A GitHub account and one repository. GitHub Pages is free, with one condition that matters: "If the account that owns the repository uses GitHub Free or GitHub Free for organizations, the repository must be public." GitHub's limits are generous for a writing site: "Published GitHub Pages sites may be no larger than 1 GB", with "a soft bandwidth limit of 100 GB per month."
  • A Claude plan with cloud sessions. Cloud sessions "are available on Pro, Max, and Team plans", and run from the browser at claude.ai/code or from the Code tab of the Claude app on a phone. They need GitHub connected; the Claude GitHub App gives them "Any public repository, and private repositories that the Claude GitHub App is installed on".
  • A way to record and transcribe. Any app that turns a voice memo into text. I use Otter; the order you said things in, and the words you reached for, are the raw material for your voice.
  • A Stripe account and a Payment Link. The top-up page sends the reader to it; your site never sees card details.
  • Optionally, a domain. GitHub Pages serves <you>.github.io until you add one.

Step by step

  1. Create the repository and turn on Pages. A new public repository, a README, and in Settings, Pages, choose GitHub Actions as the source. GitHub's guide covers it in five steps.
  2. Add a workflow that validates before it publishes. This site's deploy workflow is the pattern: validate, then tag the release, then deploy. A small version is below. The rule that matters is that a failed check stops the release.
  3. Write the house rules. One file at the root, CLAUDE.md, which Claude Code reads at the start of every session. A template is below. This is where your voice, your verification rules and your release steps live, and it grows by one line every time you correct the agent.
  4. Connect a cloud session to the repository. At claude.ai/code, connect GitHub, choose the repository, and start a session. From then on you can do the same from your phone.
  5. Give it the first brief. Paste the brief below. The agent sets up the folders, the article template, a small build script that turns Markdown into pages, and a validator, and publishes a first page about you.
  6. Record, paste, review. Record a memo, paste the transcript into the session, and read what comes back on your phone. Correct it by voice. The agent changes it, rebuilds, validates, pushes, and checks the live page.
  7. Add the meter. When there is something worth paying for, add the reader meter (next section).
  8. Keep the record. Every article ends with what it does not claim and where it comes from; a correction is a new version of the article, with its diff, not a note about the old one; every release gets a version and a one-line note.

The workflow, small enough to read:

name: deploy-pages
on:
  push:
    branches: [main]
permissions:
  contents: read
  pages: write
  id-token: write
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python3 build/validate.py
  deploy:
    needs: validate
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: site
      - id: deployment
        uses: actions/deploy-pages@v4

The house rules

The file the agent reads first is what turns a general model into your writer. This site's version grew from every mistake that added a rule, and How the voice works explains why the voice comes from the memos, not from a setting. A starting point:

# House rules

## Who I am
[Two paragraphs: your field, your years in it, what you are building and for whom.]

## The voice
- Write as me, in the first person, from my voice memos, keeping my order and my phrases.
- Plain words. British spelling. No em-dashes. Never overstate.

## Before writing
- Check every fact, number, name and date against a source. Link it.
- Where my memo is wrong, correct it and say so in the article.
- Mark what exists, what is planned, and what is only my recollection.

## Never publish
- Anything confidential: client names, case details, transcripts, contracts,
  private messages, personal data. This repository is public.
- Keys, passwords or tokens. Scan the staged diff before every commit.

## Every article
- A title, a summary, "In short", the argument in sections,
  "What this does not claim", and "Where this comes from".
- A correction is a new version: republish the article as it should read now, and let the version history and its diff show what changed. Nothing is silently changed.

## Every release
1. Build and validate. Stop on any failure.
2. Bump the version and add a one-line release note.
3. Commit, push, and check the live page loads.

And the first brief, to paste into the first session:

Set up this repository as my personal site, written from my voice memos.
Read CLAUDE.md first and follow it. Create: content/articles/ for Markdown
articles with front matter; build/build.py to render them into site/ as
static HTML with an index, an about page and an RSS feed; build/validate.py
to check links, front matter and that no secret-looking string is in site/;
and the GitHub Actions workflow in .github/workflows/. Then write the first
article from the memo below, build, validate, commit, push, and tell me
the live URL once it loads.

Readers who pay a little

The payment side is already packaged, at api.newsroom.sgit.ai. It is a client-side API: versioned files a site loads and pins, which run "in the reader's browser, with no server of ours". The reader starts with credit, pays a few pence a page by how far they read, rates the page, and the rating moves the price; for publishers the defaults are "£5 of credit to begin", 5p an article and 10p when new. Top-ups go through "a Stripe Payment Link you own". The developer quick start puts it on a page with a config and one import, pinned to a release:

<sg-meter view="balance"></sg-meter>
<sg-meter view="page" kind="article" date="2026-10-15" title="The page's title"></sg-meter>
<script type="application/json" id="sg-meter-config">
{"storageKey": "mysite.meter.v1", "start": 500, "symbol": "£",
 "prices": {"article_new": 10, "article": 5, "page": 1, "free": 0},
 "topup": {"amount": 500, "link": "https://buy.stripe.com/6oUfZ9ez65vVgU2fY15os04"}}
</script>
<script>
  const release = 'https://api.newsroom.sgit.ai/v0.2.5/';  // the pinned release: change it in one place
  import(release + 'assets/components/sg-meter/v1/v1.4/v1.4.0/sg-meter.js');
</script>

Put your own Stripe Payment Link in topup.link; while it is empty, no money moves. It is an honesty box, not a paywall: it never blocks a page, and because the balance is in the reader's browser, a reader can change it. That is the deliberate trade, explained in paying after the value: people who find it useful pay a little, and nobody is kept out. The same release also has reading lists in a link, personas, search and an encrypted vault for readers who want to carry their account between devices; add them when they are useful.

One condition to know. GitHub says Pages "is not intended for or allowed to be used as a free web-hosting service to run your online business", or a site "primarily directed at either facilitating commercial transactions or providing commercial software as a service". A writing site with an optional meter is primarily writing; if yours becomes primarily a shop, move it to a host that allows that. The files are static, so they move anywhere.

A behaviour policy for your agents

The house rules are a start. The next step is to write them as an Agent Behaviour Policy: a versioned file that says what the agent is given, what it is for, and what it must not do, with each rule marked by what keeps it. It does two jobs at once, and both matter for a founder.

The first is security. An agent that publishes for you needs real privileges: it can push to your repository, which means it can publish anything to your site. The policy is where you write down exactly what it is granted and what it is not: push to the one repository, never to another; publish from the main branch only after the checks pass; never hold your Stripe keys; never commit a key, a password or a client's name. A policy beside the prompt argued that every agent should take one as an input, and the policy draws the liability line: what the agent was allowed to do is what you are accountable for.

The second is the business logic, and this is where it becomes yours. A behaviour policy is not only a security control; it goes all the way down to how you want the work done. You can write that you do not want more than one post a day; that the tone is warm, plain and first person; that every claim about a client needs their written permission; that nothing goes out on a Sunday; that every article ends with what it does not claim. These are the instructions you would give a new member of staff, written once, in a form an agent can follow and a person can check. Commander's intent is a behaviour policy makes the same point from the other end: say what you want achieved and the limits, and let the agent work inside them.

# Behaviour policy: my site (v1.0)

## Grant
- Push to github.com/me/my-site, branch main. Nothing else.
- Read my drafts vault. Never write to it without asking.

## Mandate
- Turn my voice memos into articles in my voice, check them, publish them.

## Rules  [barrier: expectation = the agent keeps it, setting = a hook keeps it]
1. At most one new article a day.                        [setting: pre-push hook]
2. Every fact has a source link; correct my memo where it is wrong.   [expectation]
3. Tone: warm, plain, first person; British spelling.    [expectation]
4. Never publish a client's name without written consent. [expectation, checked by the editor]
5. Leak scan before every commit: no keys, no client data. [setting: pre-commit hook]
6. Every release is built and validated before it is pushed. [setting: CI]

It also lets you split the work, as this site does, across more than one agent. A writer turns the memo into a draft; an editor checks it against the rules, the sources and your voice, and can send it back; a publisher is the only one granted the push, and only for drafts the editor has passed. Each has its own section of the policy and its own grant, so the agent that writes cannot publish on its own, and the one that publishes cannot invent. This newsroom works the same way, with named agents for writing, the wire and the design, each with its own page; the agents write too describes them.

The policy is enforced in two ways, and the difference is worth knowing. The simplest is the prompt: the policy is read at the start of every session and summarised on every prompt, which is how this site's own writing session works, under a policy of eleven rules that is re-read after every summary and reports its status every few answers. That keeps the rules in view, but it is still the agent keeping them. The stronger way is a hook: a small program the agent's environment runs before and after each action, which blocks a push on a second article in a day or a commit that contains a key, whatever the agent intended. Are hooks the sweet spot? moved this site's own policy into hooks, rule by rule, and more than half of its rules could move. Mark each rule by which of the two keeps it, and you know which ones to trust.

Further: a private vault beside the public site

A more advanced setup keeps everything that should not be public out of the public repository altogether. The repository holds what is published. Beside it, an sgit vault holds the rest: drafts you are not ready to show, transcripts of the interviews the agent ran with you, the data an article was built from, notes about clients, the guidance and examples you want the agent to learn your voice from, and the agent's own working files. A vault is encrypted on your machine before anything is uploaded, versioned like git, and opened only with its key, so the server that stores it cannot read it.

The workflow stays the same, with one more step. The agent session clones the vault with a key you give it through the environment, never in a file in the repository; it writes the draft and its working material into the vault; the editor reads it there; and only when an article is approved does the publisher copy the final text into the public repository. Nothing private ever touches the public history. This is how this site's own writing session keeps its working material: scripts, figures, measurements and reviews in a vault of its own, while only the articles reach the site. And because a vault can publish a read-only key on purpose, you can choose to share a single folder, a data set behind an article, say, without sharing the rest. Agent workflows on ephemeral vaults goes further, with seven architectures from one agent to a swarm.

What it is like to run

On this site, in three days, 54 messages from me, ten of them voice memos, became 40 releases, each with figures, sources and a section on what it does not claim. The memo is a draft of a thought; the article is the thought, checked. Two habits make the biggest difference. Ask the agent to interview you when a story is thin: a session acting as a journalist, challenging every answer, is how Ten hard questions for RiskMandate was written. And let the record build on itself: every article links to the ones before it, so the history is not a list of posts but a map of the path, which is what Omnichannel programming means by one shared state.

What this does not claim

  • The writing pipeline is not a kit yet. This site's generator and release steps are published as a pattern; the brief above has the agent build a smaller one.
  • The meter trusts the reader. Balances can be edited, and the return page does not verify a payment, both by design.
  • Costs vary. GitHub Pages is free within its limits; a Claude plan, a domain and Stripe's fees are not.
  • A public repository is public. On a free plan, Pages needs it; nothing confidential belongs in it.
  • A rule in a prompt is a hope. Only the rules a hook or CI keeps are enforced; mark which is which.
  • Updated on 15 October. Added the behaviour policy and the private vault.
