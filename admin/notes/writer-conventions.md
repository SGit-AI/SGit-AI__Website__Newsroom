# Writer conventions (newsroom.writer)

Standing requests from the editor, kept here so they survive a new session. Start with the handbook, `admin/content/articles/how-a-journalist-agent-publishes-here.md`, and the tools in `admin/writer/`.

- **An article that answers or debriefs a post shows the post.** When an article responds to someone's post (LinkedIn or elsewhere) and the editor has shared a screenshot, crop the post itself (author, title, text, the image if it carries the point) and put it at the top as a `| medium | aside` shot on the right, with the post's words in the caption. Mask the viewer's own UI (menus, close buttons, the viewer's avatar, the reaction bar). The aim is that the person whose post it is recognises it at once and is glad to share the article. Since 27 October 2026 (Jeremiah Grossman, Tami Hoffman).
- **External reviews go on the record.** When the editor pastes a review from another model, file it under `admin/content/articles/reviews/<slug>/` as that reviewer's record, answer each finding in `status.json`, correct the article in a new version, and add a short "Reviewed, and corrected" section saying what changed and where we disagree.
- **Figure captions are at most 120 characters.** The caption (the third field of a `!shot` or `!frames` line, also the image's alt text) says what the image is: "EPSS scores for the 1,383 CVEs in the window." The numbers and the argument go in the text. Long captions overflowed the column beside a figure and could not be carried into a LinkedIn article or newsletter. Checked by `admin/build/validate.js` (check 14) and listed by `python3 admin/build/captions.py`. Since 27 October 2026.
- **CI owns the version.** Never write a release number: run `admin/build/release_stamp.py --pending`, give a new article the pending version from `version.txt`, and commit with a subject that has no number. CI numbers, tags and deploys (`admin/notes/2026-10-27__ci-owns-the-version.md`).
- **Build from full history, and finish with chrome and the validator.** A shallow clone of this repository or of sgit.ai makes `publish.py` drop the older version pages (784 of them on 28 October): `git fetch --unshallow` both first. `search_index.py` writes `search/index.html` without its nav, so run it before `chrome.py`, or re-run `chrome.py`, the sitemap, `llms-full` and `node admin/build/validate.js` after it; the last command before the commit is always the validator (v0.13.124).
- **A vault key goes to the vault registry, not to the editor.** Seal it with `pki-agent.mjs seal --to sha256:956934e47063ceaa --from-vault <folder> --name "vault key: <name> (<id>)" --qr <file>.png` (the DC Vault Registry, "the vault of vaults"), after `pki-agent.mjs trust` shows it chains to the editor's root; its link to the root was valid until 30 October 2026, so check it again each time. Give the editor the sealed QR for the registry's session (28 October, vault m1wbrefr).
- **No `.html` source under `admin/notes/`.** Every `.html` file in the repository is served and checked as a page; keep a vault's page source as `index.html.txt` beside its other files.
- **Revising a published article: keep code spans with angle brackets whole, and land the revision as one commit.** A version page shows a word diff, and a sentence reworded around `` `git commit <paths>` `` split the code span and leaked `<paths>` as raw HTML, which sgit.ai's validator refuses (MD-HTML). Keep such a span unchanged, or write the new text without angle brackets. The build makes a version for every commit that touched the article, so a broken intermediate commit stays broken even after a fix: squash a revision onto `origin/dev` (`git reset --soft origin/dev`) before building, and push it to `dev` as one commit (v0.13.128).
