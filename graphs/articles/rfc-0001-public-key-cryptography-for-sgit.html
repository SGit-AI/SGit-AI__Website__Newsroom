Proposals (6)

  • proposalBoth designs share a first step: a vault signing key, an Ed25519 key derived from the passphrase along a third path, with writers signing branch pointers and the index.“today's vaults can get a vault signing key: an Ed25519 key derived from the passphrase along a third path” § top
    Encryption and keys 70Provenance and evidence 99
  • proposalDesign 1, native PKI vault mode: two key pairs, neither derivable from the other, X25519 for reading and Ed25519 for writing, so a reader cannot write and a host cannot forge.“Two key pairs, neither derivable from the other: one for reading, one for writing.” § top
    Native PKI vault modeEncryption and keys 70sgit 91
  • proposalThe write-only depositor is the capability today's design cannot express: it can encrypt but not read, so write-only means append to its own inbox branch.“A depositor can encrypt but not read, so it cannot read the current tree to change it: write-only means append.” § top
    Native PKI vault modeVault design 48
  • proposalDesign 2, sealed files: an inner envelope sealed to named people's public keys inside the vault's own encryption, on either vault mode, with the private key anywhere.“An inner envelope, sealed to named people's public keys, inside the vault's own encryption.” § top
    Sealed filesEncryption and keys 70Identity and secrets 59
  • proposalThe proposed format is age v1: specified, small and audited, openable with the stock age tool, with a plugin protocol for keys that live elsewhere.“It is specified, small and audited; a sealed file can be opened with the stock age tool without sgit” § top
    Sealed filesage 2
  • proposalThe same envelope can carry a vault capability to a person: sgit share --to dinis would seal it to Dinis's published key, so no passphrase passes through chat or shell history.“sgit share --to dinis would seal it to Dinis's published key, so no passphrase passes through chat, the command line or shell history.” § top
